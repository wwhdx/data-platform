## 1. 现状诊断

### 1.1 两端现状

| 维度 | data-platform | 望野主平台 |
|------|-------------|-----------|
| 运行时 | Fastify :3400 | Next.js 14 :3000 |
| 数据库 | PostgreSQL `data_platform` | PostgreSQL `lumina_dev`（Prisma） |
| 认证 | 无（内部服务） | next-auth v5（JWT session） |
| 部署 | 独立 docker-compose | 独立 docker-compose |
| 搜索引擎 | pgvector + tsvector + RRF | PostgreSQL FTS + Serper API |
| Connector | OpenAlex 1个（/17 规划） | 无 |

### 1.2 集成断层

- `src/adapters/engineCore.ts` 提供了 `createDataPlatformSearchProvider()`，但**主平台全量 `src/` 搜索 `data-platform`/`3400`/`SearchProvider` 命中数为 0**
- engine-core 工作流的 `search` 节点调用 `ctx.services.callSerper()`，未使用 data-platform
- 主平台 `docker-compose.yml` 不包含 data-platform 服务
- 两端数据库完全独立，无联邦查询

### 1.3 断层根源

data-platform 设计为 engine-core 的 `SearchProvider` contract 实现者，但主平台 engine-core 的 `EngineServices` 接口定义了 `callSerper` + `searchSemanticScholar` 两个具体搜索方法，**没有预留通用的 `searchProvider` 注入点**。适配器存在但上游无插槽。

**核心原则**：
- data-platform 通过 HTTP API 对外服务，**不共享数据库**
- 主平台通过 `DataPlatformClient` 消费，**不直连 data-platform 数据库**
- engine-core 新增 `searchProvider` 注入点，替代 hardcoded 的 `searchSemanticScholar`

## 3. 集成点设计

### 3.1 集成点矩阵

| 集成点 | 主平台入口 | data-platform 接口 | 优先级 | 说明 |
|--------|----------|-------------------|--------|------|
| **A. 文章生成知识注入** | engine-core 工作流 `buildPrompts` | `POST /api/search` | **P0** | 替代/补充 Serper，为 LLM 提供深度知识上下文 |
| **B. 全局搜索扩展** | `GlobalSearchBar.tsx` SWR | `POST /api/search` | P1 | 用户搜索时同时返回外部知识结果 |
| **C. 行业页面数据富化** | `IndustryPageClient.tsx` SWR | `POST /api/search` | P2 | 行业页展示该领域最新论文/专利/数据 |
| **D. 管理后台数据源监控** | `admin/` server component | `GET /api/sources` + `/api/admin/stats` | P1 | 管理后台查看数据采集状态和文档统计 |
| **E. 管理后台手动采集** | `admin/` server action | `POST /api/admin/collect` | P2 | 管理后台触发数据源采集 |
| **F. 定时采集调度** | data-platform 内部 cron | 无需集成 | P0 | 每日自动增量采集（已实现） |

### 3.2 集成点 A（文章生成知识注入）— 详细设计

这是**最高价值集成点**。当前主平台 engine-core 工作流在 `buildPrompts` 中仅使用 `callSerper()` 获取实时网络搜索结果。接入 data-platform 后，工作流同时从知识库获取深度内容。

**当前流程**：
```
工作流 buildPrompts
  └→ callSerper(query) → 网页搜索结果 → 注入 prompt
```

**目标流程**：
```
工作流 buildPrompts
  ├→ callSerper(query) → 网页搜索结果（实时性）
  └→ searchProvider.search(query) → 知识库结果（深度、可溯源）
  └→ 合并去重 → 注入 prompt
```

**改造点**：

1. **engine-core `EngineServices` 接口扩展**（`src/engine/types.ts`）：
   ```typescript
   // 新增通用 SearchProvider 注入点
   searchProvider?: {
     search(query: string, opts?: { maxResults?: number }) => Promise<SearchProviderResult[]>;
   };
   ```

2. **`src/engine/services/defaultServices.ts` 注入**：
   ```typescript
   import { createDataPlatformSearchProvider } from "@wangye/data-platform/adapters/engineCore";
   
   const dataPlatform = createDataPlatformSearchProvider(
     process.env.DATA_PLATFORM_URL ?? "http://localhost:3400"
   );
   
   export const defaultServices: EngineServices = {
     // ...existing...
     searchProvider: dataPlatform,
   };
   ```

3. **工作流 `buildPrompts` 节点**（需确认具体文件路径）：
   ```typescript
   const [webResults, kbResults] = await Promise.all([
     ctx.services.callSerper(query),
     ctx.services.searchProvider?.search(query, { maxResults: 5 }) ?? [],
   ]);
   ```

### 3.3 集成点 B（全局搜索扩展）— 详细设计

用户在主站搜索框搜索时，同时展示 data-platform 外部知识结果。

**改造文件**：`src/components/search/GlobalSearchBar.tsx`

**方案**：
```
用户输入 "transformer attention"
  ├→ GET /api/search/suggest → 平台内文章/标签建议
  └→ POST {data-platform}/api/search → 外部论文学术结果
  └→ 合并展示（平台结果在上，外部结果在下，分区显示）
```

**是否需要服务端代理**：是。建议新增 `src/app/api/search/external/route.ts` 代理 data-platform 搜索，原因：
- 隐藏内部服务 URL
- 统一鉴权（防止未登录用户消耗搜索配额）
- 统一日志/审计

### 3.4 集成点 D（管理后台数据源监控）— 详细设计

管理后台新增 "数据源" 页面，展示 data-platform 的各数据源状态和文档统计。

**方案**：
- Server Component 通过 `fetch` 直接调用 data-platform 的 `GET /api/sources` + `GET /api/admin/stats`
- 可选：通过 Next.js API Route 代理（便于加权限校验）
- 管理后台侧边栏新增菜单项（`admin/layout.tsx` 的 NAV_PERMISSIONS + `<Link>`）

```
望野根 docker-compose.yml
```

**网络**：所有服务在同一 Docker 网络，data-platform 通过服务名 `dp-app:3400` 访问。

### 4.2 环境变量

主平台 `.env` 新增：
```bash
DATA_PLATFORM_URL=http://dp-app:3400   # Docker 内部
# 本地开发: http://localhost:3400
```

### 4.3 可选：独立部署模式

如果不想在开发环境跑全套 data-platform（Ollama 模型较大），支持降级：
- `DATA_PLATFORM_URL` 为空 → DataPlatformClient 返回空结果，不影响现有功能
- 所有调用侧均做空值保护

## 5. 数据流安全边界

### 5.1 网络隔离

```
公网 → :3000 (Next.js) → 内部网络 → :3400 (Fastify)
                               ❌ 公网不可直达 :3400
```

- data-platform 不暴露公网端口
- 仅在 Docker 内部网络可达
- Next.js 服务端组件/API 路由作为唯一入口

### 5.2 鉴权方案

data-platform 目前无鉴权。两种方案：

| 方案 | 实现 | 适用场景 |
|------|------|---------|
| **A. 共享 Secret** | 主平台请求时带 `Authorization: Bearer {DATA_PLATFORM_SECRET}`，data-platform 中间件校验 | MVP 快速接入 |
| **B. 网络隔离** | 仅 Docker 内网可达，data-platform 不暴露公网端口 | 简单，依赖 Docker 网络 |

**推荐 MVP 使用方案 B**，后续按需升级到 A。

### 5.3 许可合规透传

data-platform 搜索结果已包含 `license` + `commercialUse` 字段。主平台使用这些数据时需：
- 文章引用外部知识时标注来源和许可
- 付费内容保护（商用受限数据不进入付费全文）

这部分在 engine-core 工作流的 `validateCitationRefs` 节点中已有处理框架。

## 8. 关键设计决策

### 8.1 为什么用 HTTP 而不是共享数据库？

- **松耦合**：data-platform 可独立扩缩容、升级、替换
- **安全边界**：采集侧故障不影响主平台
- **网络隔离**：data-platform 不暴露公网
- **数据归属清晰**：data-platform 拥有采集数据，主平台拥有用户/文章数据

### 8.2 为什么新增 searchProvider 注入点而不是替换 callSerper？

- **互补关系**：Serper = 实时互联网搜索（新闻、最新动态），data-platform = 深度知识库（论文、专利、统计数据）
- **降级安全**：两个源各自独立降级，一个故障不影响另一个
- **引用真实性**：data-platform 结果带许可溯源，比网页搜索更适合学术引用

### 8.3 为什么搜索需要 Next.js 代理？

- **安全**：不暴露内部服务 URL 给浏览器
- **鉴权**：确保只有已登录用户消耗搜索
- **审计**：统一日志记录
- **合规**：许可信息传递给前端，辅助引用合规检查

## 9. 风险与缓解

| 风险 | 影响 | 缓解 |
|------|------|------|
| Ollama bge-m3 模型下载慢 | 首次部署耗时长 | dp-ollama-init 容器自动 pull；离线可跳过 |
| data-platform 不可达 | 搜索/生成功能降级 | 所有调用侧返回空数组，不阻塞 |
| 嵌入维度不匹配 | bge-m3=1024d vs 其他模型 | data-platform 锁定 bge-m3 默认，模型变更需重建向量 |
| 许可合规 | 商用受限数据被误用 | 搜索结果带 `commercialUse` 字段，工作流过滤 |
| Docker 资源占用 | 多 3 个容器 + Ollama 模型 | 开发环境可选禁用 data-platform 服务 |
