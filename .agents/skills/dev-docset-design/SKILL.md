# Dev Docset Design（多会话开发任务的文档集设计）


## 要解决的问题


在跨多次会话的开发任务里，agent 会自然而然地产生好几份 markdown 文档来保存上下文：问题出在哪、为什么、方案怎么定的、怎么复现/测试、现在做到哪一步了。如果不加约束，这些文档会各自生长，逐渐开始重复记录同一批事实——同一组测试结果出现在三个文件里，同一份 commit 列表出现在两个文件里，每份文档头部的"最后更新"日期每次收工都要挨个改一遍才能保持一致。


真正的问题从来不是"文档太多"，而是**没有哪个文件对某一类事实拥有唯一归属权**，导致"保持一致"本身变成了额外的维护负担，而且极容易漏改、改岔。


## 四类信息，四个归属


开发任务里绝大多数值得写下来的内容，都能归到下面四类之一。原则很简单：每一类信息只应该有一个家。如果发现同一个事实在两个文件里都写了一遍，这是需要修的信号，不是可以接受的状态。


1. **问题/背景**——这件事为什么需要做、现状是什么、有哪些约束。基本一次写完，之后很少变。
2. **设计/决策**——最终决定怎么做、每条决定背后的依据。只有设计本身变了才需要改，不该因为"跑了一次测试"或"合并了一个 commit"就去碰它。
3. **操作/手册**——环境怎么搭、命令怎么跑、怎么复现。应该是纯步骤描述，不嵌入具体的运行结果数字——结果会变，步骤除非流程本身变了否则不会变。
4. **状态/计划/日志**——现在做到哪一步、下一步是什么、已经发生了什么（跑分数字、commit、验证记录）。这是四类里唯一"理应每次收工都更新"的文件。


把第 4 类以外的内容塞进"每次都要碰"的文件，或者把第 4 类内容散落到别处，都会导致同一份事实需要多头维护、多处对齐。


## 推荐的基线结构


用内容种类命名即可，不需要在文件名上体现具体项目名或阶段代号：


- `problem.md`（可选）——只有"为什么这件事目前不成立/为什么需要做"本身值得单独写一份说明时才需要；很多任务不需要独立这一份。
- `design.md`——技术方案：最终决定了什么、每条决定的依据、关键数据结构或接口设计。
- `dev.md`——操作手册：环境、脚本、复现步骤。不出现"跑出来的具体数字"。
- `plan.md`——唯一的"当前状态"权威来源：任务表、commit 列表、验证结果、下一步计划。


不是每个任务都需要凑齐四份，见下面"什么时候一份就够"。


## 防重复的具体规则


- 验证结果/跑分数字/commit 列表 → 只写在 `plan.md`。`design.md`/`dev.md` 里如果要提，用一句"结果见 plan.md"代替贴数字，避免两处数字慢慢对不上。
- "还没验证的项/待办" → 只维护在 `plan.md` 的任务表里，不要在 `design.md` 里再单独搞一份"未验证项"清单，两份 TODO 迟早会走岔。
- 对早期结论的勘误/修正 → 直接在 `design.md` 对应段落原地改掉，不要另开一个"勘误"小节，也不要在 `plan.md` 里把同样的勘误再复述一遍。
- 某份文档如果已经不再有新内容进来（比如最初的问题分析已经被后续设计完全取代），按后面"归档"一节的具体条件处理，不要让一份事实上已经"死"的文档还继续背着"是否需要更新"的心智负担。


## 例外：并行/隔离的子任务允许故意冗余


上面的"同一个家"规则有一个前提：这套文档由同一条主线（同一个 agent 或同一个人）持续维护，随时能互相对照、互相更新。如果文档是要拆给彼此不共享上下文的并行子任务或子 agent 分别执行——比如把一个大任务拆成几个可以独立开工的子任务，各自只读自己那一份——把该子任务需要的背景、约束、验收标准完整复制进它自己的文件反而是对的：这时候执行者不需要、也不应该跳出去读别的文件才能知道自己要干什么。去重规则和这种"自包含"解决的是两个不同的问题：去重防止同一条主线里的事实跑偏，自包含是为了让隔离的执行者不必依赖外部上下文。判断哪种情况适用，看这份文档之后是谁在读、读的时候能不能顺手参照别的文件——能参照就去重，不能参照（要脱离上下文独立执行）就允许冗余。


## 写之前先查一遍：轻量一致性自查


往任何一份文档里写一个具体数字、commit、结论之前，先花几秒钟在整个文档集里搜一下这个事实是不是已经出现过（比如搜这个 commit hash、搜这个百分比数字、搜这项"待办"的关键词）。搜到了，要么它本来就该在那，不用重写一遍；要么说明找到了一处该更新但还没更新的旧记录，去改那一处，而不是在当前文件里再加一份。这个动作比事后靠"漂移信号"去发现问题便宜得多——漂移信号是用来检查已经存在的文档集有没有出问题，写前自查是用来防止新问题产生。


## 命名原则：按内容种类命名，别按任务/阶段代号命名


如果用任务或阶段代号给文档命名（比如某个阶段的编号），这份文档会在推进过程中不知不觉地从"这个阶段最初要交付的规格"膨胀成"这个阶段所有活动的日志"——因为文件名本身就在暗示"这是某阶段的产出"，写的人会习惯性地把这个阶段发生的一切都往里塞，包括后续才产生的验证结果、commit 记录，而这些其实该属于 `plan.md`。用内容种类命名（design/dev/plan）能从命名层面就限制住每份文档该装什么，不随阶段推进而蔓延。


## 漂移信号


看到下面任何一条，说明文档集已经开始重复维护同一批事实，该收敛了：


- 同一个事实需要改一个以上的文件才能保持一致
- 某个"最后更新"字段几乎每次收工都要在好几个文件里各改一遍
- 某份文档里专门有一节在"对照另一份文档的旧结论做勘误"
- "下一步/未验证项"清单在一个以上的文件里都存在
- 一份文档的文件名是任务/阶段代号，而不是内容种类


## 什么时候一份就够


任务小、预计一两次会话就能收尾时，不需要拆成四份——一份文档按"背景 → 方案 → 怎么验证 → 当前状态"的顺序写下去就够了。只有当某一类内容本身开始变得庞大、或者更新频率明显和其他部分不一样时（比如"怎么复现"几乎不变，但"当前状态"每天都在变），才值得把它拆成独立文件——判断标准是"更新节奏是否不同"，不是"篇幅是否够长"。


## 收敛一批已经存在、已经开始重复的文档


1. 把每份文档按段落标出属于上面四类里的哪一类。
2. 把明显放错地方的内容（比如手册里嵌的跑分结果、设计文档里的验证日志）搬到它该在的文件里。
3. 对于同一事实在多处出现的情况，选一处作为权威来源，其余地方改成一句引用，删掉重复的数字/清单本身。
4. 如果某份文档收敛完之后已经没有活的内容了，按下面"归档"一节的触发条件和产出形式处理，不要留着一个不会再更新、但还占着"是否过期"心智负担的文件。


## 归档：具体触发条件与产出


"折进附录"不该只是一句原则，要有明确的触发条件和产出形式，否则会一直停留在"要不要现在归档"的犹豫里：


- **触发条件**：某份文档连续两次收工都没有产生新内容，或者它的结论已经被另一份文档完全取代（比如最初的问题分析被后续设计方案取代）。
- **产出形式**：不是删除，而是在权威状态文档（`plan.md`）里加一个带日期的历史小节，把原文档的结论压缩成几句话搬过去；原文档顶部加一行"已归档，见 plan.md 某年某月某日小节"，之后不再修改它。
- 归档是终态，不是"先冻结、以后可能还会改回来"的中间态——一旦归档就不再期待它更新，否则又会变回"要不要碰它"的心智负担。


## 归属速查表


可以直接抄到 `plan.md` 顶部，作为后续每次收工前的自查清单：


| 内容类型 | 唯一归属 |
|---|---|
| 为什么要做这件事、背景与约束 | `problem.md`（如果存在） |
| 最终技术方案、每条决定的依据 | `design.md` |
| 环境搭建、命令、复现步骤 | `dev.md` |
| 当前状态、任务表、commit、验证结果、下一步 | `plan.md` |


写文档前先问一句"这属于哪一类、它的家在哪"，比事后再去查重复要便宜得多。
